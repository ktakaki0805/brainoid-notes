# チケットを実装する

対象のチケット：`$ARGUMENTS`

IDが指定されていなければ、`pnpm tickets:next` の結果を見せて、どれを進めるかを聞く。勝手に選ばない。

1チケットが1コミット。手順の全体は `docs/dev/workflow.md` にある。

`/implement-tickets` からまとめて呼ばれているときは、下の手順で「報告して指示を待つ」「聞く」とある箇所を、そのskillの読み替えの表に従って扱う（飛ばす、または全体を止める）。

## 役割

このskillを実行しているあなたは、進行役です。コードを書かず、レビューもしません。

| 役割     | だれが                                | すること                                                                 |
| -------- | ------------------------------------- | ------------------------------------------------------------------------ |
| 進行役   | あなた                                | 着手の確認、サブエージェントへの依頼、繰り返しの管理、最後の検査、コミット |
| 実装     | `ticket-implementer` サブエージェント | コードとテストを書く。レビューの指摘を直す                               |
| レビュー | `ticket-reviewer` サブエージェント    | 差分を読み、検査を実行し、受け入れ条件を確かめて判定する。ファイルは変えない |

## 必ず守ること

- **実装とレビューを、同じサブエージェントにさせない。** あなたが肩代わりもしない。実装が足りなければ実装のサブエージェントに、判定が要るならレビューのサブエージェントに頼む。
- **ブランチを切らない。PRを作らない。** `main` の上で作業し、`main` に直接コミットする。
- **プッシュしない。** `git push` を実行しない。プッシュは人がする。
- **コミットするのはあなただけ。** レビューが「承認」になったあとに、1回だけコミットする。承認されていない変更をコミットしない。

## 1. 着手できるかを確かめる

チケットのファイル（`docs/tickets/` のそのID）と、「参照」にある設計書を読む。

次のどれかに当たったら、進めずに報告して指示を待つ。

- `status` が `todo` ではない。ただし、`in-progress` で `owner` が自分、作業ツリーに変更が残っているなら、前回の続きである。続けるかどうかを聞き、続けるなら「4. レビューと修正を繰り返す」から始める。
- `depends_on` に、`done` でないチケットがある（`pnpm tickets:next` に出てこない）。
- 「未決事項」が「なし」ではない。何を決める必要があるかを示し、決めてもらう。
- 参照した設計書の、このチケットに関わる箇所に「案」「未決」とある。その案で進めてよいかを確かめる。
- いまいるブランチが `main` ではない。
- 作業ツリーに、コミットしていない変更がある（`git status --porcelain` が空でない）。

リモートがあれば、最新を取り込む。

```bash
git fetch origin
git status -sb          # origin/main より遅れているか、分かれているかを見る
git pull --ff-only      # 遅れているだけのときに限る
```

- 手元にプッシュしていないコミットがあり、`origin/main` と分かれているときは、止めて報告する。`rebase` や `merge` を勝手にしない。
- 取り込んだら、チケットの `status` を読み直す。ほかの人が終わらせているかもしれない。
- リモートがない、つながらないときは、確かめられなかったことを控えて続ける。

## 2. 着手の印を付ける

チケットの `status` を `in-progress`、`owner` を `git config user.name` の値にする。ここではコミットしない。最後のコミットに含める。

## 3. 実装を頼む

`ticket-implementer` サブエージェントを起動する。次を渡す。

- チケットのIDと、ファイルのパス
- 1で人に決めてもらったことがあれば、その内容（設計書かADRにも書くように頼む）
- コミットしない、プッシュしない、チケットの `status` を変えない、ということ

報告が「止めた」なら、繰り返しに入らず、理由を人に報告して指示を待つ。作業ツリーの変更は残す。

## 4. レビューと修正を繰り返す

レビューは3回まで。

1. **レビューを頼む。** `ticket-reviewer` サブエージェントを、毎回新しく起動する。次を渡す。
   - チケットのIDと、何回目のレビューか
   - 2回目以降は、前回の指摘の一覧と、実装のサブエージェントが「直さなかった指摘とその理由」

   実装のサブエージェントの報告は渡さない。チケットと差分だけで判断させる。
2. **判定を読む。** 「承認」なら「5. コミットする」へ進む。「要修正」なら次へ。
3. **修正を頼む。** 最初に起動した実装のサブエージェントに、続きを頼む（`SendMessage` で、そのサブエージェントに送る）。続けられなければ新しく起動し、チケットのIDも渡す。
   - 指摘は、レビューが返したとおりに渡す。要約しない。取捨選択しない。
   - 「必ず直す」は全部直すこと、同意できない指摘は直さずに理由を書くこと、を伝える。
4. 1に戻る。

次のときは、コミットせずに止めて、人に報告する。

- 3回目のレビューでも「要修正」だった。
- 同じ指摘について、レビューが「維持する」、実装が「直さない」となった。どちらが正しいかを、あなたが決めない。
- 指摘を直すのに、設計の変更か、チケットの範囲を超える作業が要る。

止めたときは、作業ツリーの変更と、チケットの `in-progress` をそのまま残す。変更を捨てない。

## 5. コミットする

レビューが「承認」になったら、次の順で進める。

1. **自分で検査する。** `pnpm check` を実行する。落ちたらコミットしない。実装のサブエージェントに直させ、もう一度レビューを通す（回数に数える）。
2. **変更の範囲を見る。** `git status --short` で、このチケットの変更だけかを確かめる。`.env`、一時ファイル、関係のないファイルが混ざっていたら、止めて報告する。
3. **チケットを完了にする。** `status` を `done` にする。`owner` は残す。
4. **コミットする。** `main` に、1コミットで入れる。

   ```bash
   git add -A
   git commit -F - <<'EOF'
   T-012: チケットの題

   何を作ったかを2〜3行で。

   受け入れ条件：4件すべて確認
   レビュー：2回（必ず直す3件を修正）
   EOF
   git log -1 --stat
   ```

5. **プッシュしない。** ここで終わり。

## 6. 報告する

- 何を作ったか（2〜3文）と、コミットのID
- 受け入れ条件ごとの結果と、確かめ方
- レビューの経過：回数、主な指摘、直したこと、直さなかったことと理由
- 「直した方がよい」のうち、残したもの
- 設計書やADRを変えたなら、どこを変えたか
- 範囲の外で見つかったこと。チケットにするかどうかを聞く（する場合は `/create-ticket`）
- プッシュしていないこと。手元の `main` が `origin/main` より何コミット進んでいるか（`git status -sb`）

コミットせずに止めたときは、どこで止まったか、残っている指摘、作業ツリーに何が残っているかを報告する。
