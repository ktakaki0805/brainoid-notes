# チケットを作る

チケットにする作業：$ARGUMENTS

説明がなければ、何をチケットにするかを聞く。

## 1. 読む

1. `docs/tickets/README.md` と `docs/tickets/_template.md`。
2. 関わる設計書（`docs/design/`）と、仕様の「対象外」（`docs/product/spec.md`）。
3. `pnpm tickets` で、すでにあるチケット。同じ作業、重なる作業がないかを確かめる。

仕様の「対象外」に当たる作業なら、チケットにせず、そのことを伝える。

## 2. 分ける

1チケットは、1回のレビューで読み切れて、1コミットで `main` に入る大きさにする。

- `S`（半日ほど）、`M`（1〜2日）、`L`（3日ほど）。Lを超えるなら分ける。
- **それだけで `main` に入れられる単位にする。** コミットしても `main` が壊れず、テストが通ること。
- **層ではなく、動きで切る。** 「表を全部作る」「APIを全部作る」ではなく、「ページを作れる」「改名できる」のように切る。ただし、純粋なロジック、スキーマ、APIの土台は、先に単独で出してよい。
- **決めることと作ることを分ける。** 設計が決まっていないなら、「未決事項」に書くか、先に決めるためのチケットにする。
- **画面とAPIは、小さければ1つにまとめる。** 大きければ、APIを先にして分ける。

## 3. 書く

1. 番号を決める。マイルストーンごとの帯（`docs/tickets/README.md`）の中で、次の空きを使う。
2. ファイル名は `T-0xx-short-slug.md`。短い英語の名前を付ける。
3. `_template.md` の欄をすべて埋める。

欄ごとの書き方：

- **title**：何ができるようになるかを書く。作業の名前（「リファクタリング」など）にしない。
- **目的**：なぜ要るのかを1〜2文で。
- **参照**：実装する人が先に読む設計書。なければ、設計書を先に書く必要がないかを考える。
- **やること**：3〜6個。設計書に書いてある詳細は写さず、指す。
- **やらないこと**：隣の作業を、どのチケットでやるかと一緒に書く。範囲が広がるのを防ぐ欄なので、必ず書く。
- **受け入れ条件**：外から確かめられる形で書く（「〜すると、〜になる」）。3〜5個。「きれいに実装されている」のような、確かめられない条件は書かない。
- **未決事項**：人が決める必要があること。なければ「なし」。
- **depends_on**：先に `done` になっている必要があるものだけ。念のための依存は足さない。

## 4. 確かめる

```bash
pnpm tickets:check
```

依存先がある、循環していない、書式が合っている、を確かめる。

## 5. 報告する

- 作ったチケットの一覧（ID、題、大きさ、依存）
- 分け方の理由を一言
- 人が決める必要があること

## 6. コミットする

報告のあとに、コミットしてよいかを聞く。よければ、チケットのファイルだけを `main` にコミットする（`チケットを足す：T-0xx 題`）。プッシュはしない。

作業ツリーに変更が残っていると、`/implement-ticket` は着手の確認で止まる。コミットしない場合は、そのことを伝える。

実装の途中で範囲の外の作業が見つかったときは、いまのチケットのコミットが済んでから、チケットを足す。いまのチケットのコミットには入れない。
